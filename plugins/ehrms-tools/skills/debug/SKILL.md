# EHRMS Debug 問題查詢與程式分析

從問題蒐集到程式碼修改完成。Git 生命週期管理（分支、lab、釋出）請使用 `/bug-fix`。

- 專案結構：See [../../references/project-structure.md](../../references/project-structure.md)
- 編碼規則：See [../../references/encoding-rules.md](../../references/encoding-rules.md)

## 核心原則

1. **需求先行**：先確認本次要完成什麼，再蒐集足以支持下一步的資訊；維運單不預設為程式缺陷
2. **先確認再修改**：討論並確認修改方案後才動手
3. **不改變商業邏輯**：除非業務邏輯有誤（需詢問使用者）
4. **證據導向**：基於錯誤訊息、Log、資料狀態分析
5. **精簡輸出**：僅顯示關鍵程式碼位置，不列完整程式碼

## 步驟 0：辨識需求與是否需要排查

先讀使用者要求、案件最新訴求及既有處理結果。Crisis／Fatal 或歷史信件中的異常不等於本次要查 bug；資料調整與異常追查為不同需求，混合案件只展開本次需要的部分。

| 類型 | 特徵 | 後續步驟 |
|------|------|---------|
| **資料查詢／調整／解鎖** | 「查目前狀態／還有三筆請修改／解鎖」 | → 1A → 操作流程／必要 SQL 或範本 → 結束；僅特定處理依據不明時讀相關程式 |
| **疑似異常** | 有具體異常事實，需釐清原因 | → 1B → 2 → 3 → 4；確認程式缺陷才進 5／6 |
| **操作／規則釐清** | 「怎麼操作／這個計算規則是什麼」 | → 1C → FAQ／設定／知識；必要時才進 2 → 結束 |
| **報表差異** | 「報表數字與預期不同」 | → 1D → 2 → 結束 |
| **DB 查詢/SQL** | 「幫我查某表格 / 寫 SQL」 | → 1E → 結束 |

先利用已提供資訊判斷；僅在缺口會影響下一步時補問，不要求資料處理單提供程式入口、錯誤訊息或重現步驟。

## 步驟 1：資訊蒐集

### 1A：資料查詢／調整／解鎖

先核對需求目的、對象與日期／單據範圍、欲查詢或調整的內容，以及前案已做的處理。缺少會影響處理的資訊才補問。

客戶明確要求修改資料或解鎖時，優先查既有操作方式及 `task_lookup` 範本；需要 SQL 才依 1E 驗證 schema。確認修改前後值、相關限制及結果核對方式，不以找到程式缺陷為前提。不因「資料不正確」就直接診斷為 bug。

完成需求分析與處理建議即可結束，不自動進入程式定位、同檔掃描或修復流程。

---

### 1B：疑似異常（原因尚未確認）

先核對異常現象、發生操作／條件、預期與實際差異及影響範圍。優先使用案件既有內容；只補問會影響判斷的缺口。

錯誤訊息、截圖、重現步驟、程式入口及近期異動有提供就採用，並非每案必填。無錯誤訊息或客戶不知道入口時，可先核對操作、設定與資料狀態；需要追碼才定位入口，不因缺少入口而停止分析。

---

### 1C：操作／規則釐清

確認想了解的操作／規則及具體場景；FAQ、設定或既有知識足以回答時直接說明。仍需釐清特定行為才進步驟 2，不固定追碼。

---

### 1D：報表差異

**必須蒐集（缺一不可）：**

| # | 項目 |
|---|------|
| 1 | 報表名稱 |
| 2 | 查詢條件 |
| 3 | 差異欄位 |
| 4 | 預期值 vs 實際值 |
| 5 | 差異範圍（全部 / 特定員工） |

```
✅ 蒐集確認：報表名稱 / 查詢條件 / 差異欄位 / 預期 vs 實際 / 差異範圍
→ 全勾後進步驟 2
```

---

### 1E：DB 查詢/SQL 產生

> ⚠️ **客戶端前提**：MCP 連線的 DB 可查詢表格結構與語法驗證，**不一定有客戶的實際業務資料**。

**必須蒐集：** 查詢目的、涉及表格或功能、查詢條件/篩選範圍

**執行流程：**
1. `search_tables` / `get_table_columns` 確認表格結構
2. `analyze_table_joins` 確認 JOIN 關係
3. 撰寫 SQL（遵循 MSSQL 2008 相容規範）
4. MCP 驗證語法（SELECT 可驗證；**INSERT / UPDATE / DELETE 僅提供語法，禁止執行**）
5. 提醒使用者在客戶端環境確認資料

**輸出格式：**
```
【查詢語法】
- 用途：[說明]
- 涉及表格：[表格清單]
- 已驗證：✅ 語法結構正確（MCP 驗證）
- ⚠️ 請在客戶端資料庫執行，MCP 資料僅供結構參考

[SQL 語法]
```

## 步驟 2：核對證據與必要的程式碼

### 2.1 查詢方向

| 問題類型 | 起始方向 |
|---------|---------|
| 資料查詢／調整 | 先核對需求、操作／範本及客戶提供資料；僅必要時核對特定程式邏輯 |
| 疑似異常 | 先確認異常事實與設定／資料條件，需要追碼才用 bug-locate |
| 操作／規則釐清 | 先 `wiki_lookup`＋`recall`，再查 FAQ／設定；Wiki 未收錄才參考 EHRMS_GIT 的 domain-knowledge；仍需確認特定行為才追碼 |
| 報表差異 | 先核對條件及客戶提供資料，必要時查 schema 或程式來源 |

### 2.2 資料來源與查詢範圍

客戶維運不使用公司 DB 查客戶業務資料或找測試資料。需要 SQL 時，依 db-query 用 MCP 確認表格結構與語法，交由客戶端執行後回填；客戶回填的查詢結果可作證據。使用者明確要求查自家環境時才查對應實際資料，並區分來源。

資料調整優先核對現況、目標值及操作影響；資料差異不直接等於程式錯誤。

### 2.3 依需求輸出

先回答需求、目前進度與下一步，不固定診斷模板。資料調整列對象／範圍、已確認狀態、處理方式及必要的待補資訊；操作／規則詢問直接說明；疑似異常區分已確認事實與待驗證方向，不先稱「問題程式碼」。

資料處理或規則說明已足以回答本次需求即可結束。跨案例可泛化的已確認規則／入口可寫入 `remember`；不把資料修改需求記成程式缺陷。

## 步驟 3：問題診斷

| 錯誤類型 | 檢查重點 |
|---------|---------|
| 功能異常 | 條件判斷、計算公式、資料來源與處理流程 |
| 執行錯誤 | 錯誤訊息、Null 值處理、型別轉換、陣列索引 |
| 資料不一致 | Transaction、Trigger、並行處理、預設值與 Constraint |
| 邏輯錯誤 | 變數值變化、迴圈邊界、條件判斷優先順序 |

1. 若有截圖，先讀取並分析
2. 先核對操作、設定及資料證據；仍不足且確需追碼時才讀相關檔案，跨層依序：ASP → VB6 → SP
3. 追碼時先確認實際行為與適用條件，只有證據支持時才定位缺陷

## 步驟 4：根因分析

識別根本原因：程式碼邏輯錯誤 / 資料狀態異常 / 環境配置問題 / DB Schema 問題 / 並行處理問題

有客製相關證據，或已核對的標準碼無法解釋行為且需要確認客製差異時，才使用 custom-locate 查詢對應版本。僅出現客戶名稱不構成客製問題的證據；限制在本次需求所需的檔案與邏輯。

## 步驟 5：診斷報告與修改方案討論

**僅已確認程式缺陷且需要提出修復方案時，使用以下 5 區塊；未確認時依 2.3 說明事實與待驗證方向：**

1. 【問題摘要】- 檔案、根因、影響（3 行以內）
2. 【問題程式碼】- 行數 + 3-10 行關鍵程式碼 + 問題說明
3. 【修復方案】- 修改前後對比 + 邏輯驗證
4. 【驗證步驟】- 測試案例 + 檢查清單
5. 【風險評估】- 影響範圍 + 風險 + 建議

**⚠️ 輸出後停止，等待使用者確認修改方案後才繼續。不可直接修改程式碼。**

### 步驟 5.1：同檔案類似問題檢查

僅已確認程式缺陷並提出修復方案後，掃描同檔案類似模式；資料調整與操作需求不執行：

1. 識別核心問題模式（條件判斷錯誤、Null 處理缺漏等）
2. Grep 搜尋同檔案類似模式
3. 若有發現：
   ```
   ⚠️ 【同檔案類似問題】
   發現 N 處：
   1. L[行數] - [說明] - 風險：[低/中/高]
   建議一併修正以避免重複除錯
   ```
4. 詢問使用者是否一併修正

## 步驟 6：執行程式碼修改（使用者確認修改方案後）

修正註解格式：
```
' yyyymmdd EHRMSONE-xxxxx modified by 修改者 for 修正內容
```

1. 確認修改者名稱（若未提供則詢問）
2. 執行程式碼修復，加入上述格式註解
3. 依據檔案編碼提供修復程式碼（不改變原始編碼，中文註解）
4. SQL 若有 DB 權限可執行部署
5. 提醒使用者執行驗證步驟

**修改完成後：**

```
✅ 程式碼修改完成。
後續 Git 操作（建立分支、commit、merge to lab、測試報告、釋出）
請使用 /bug-fix EHRMSONE-XXXXX 繼續。
```

## 資訊不足時的處理

1. 明確告知缺少哪些資訊及影響
2. 提供替代蒐集方式（例如「若不知道工號，可提供姓名讓我查」）
3. 在有限資訊下進行初步分析，標註不確定部分
4. **不因資訊不足而完全拒絕分析**

## 與其他 Skill 的協作

| 情境 | 動作 |
|------|------|
| 需要定位程式碼 | 使用 bug-locate skill |
| 涉及考勤業務規則 | `wiki_lookup`；Wiki 未收錄再參考 EHRMS_GIT 的 domain-knowledge |
| 需要 DB 查詢 | 遵循 db-query skill |
| 懷疑是客戶客製導致行為與標準版不同 | 使用 custom-locate skill |
| 程式修改完成，進入 Git 流程 | 呼叫 /bug-fix |
