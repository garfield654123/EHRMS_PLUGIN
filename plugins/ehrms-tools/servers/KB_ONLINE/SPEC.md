# EHRMS 線上知識庫 MCP：規格與計畫

> 決策日期：2026-11-20　決策者：子平
> 這份文件是決策的正本。討論過程在 `C:\D\FAQ_web\memory_review\討論清單_線上知識庫MCP.md`。
> 修改決策時請更新這份文件，並在「變更紀錄」加一行。

## 1. 目標

- 同事接上一個網址就能使用 EHRMS 知識庫，不用下載 plugin。
- 每次使用都在伺服器端留下紀錄。
- 先累積資料；驗證與整理之後交給「知識庫清理 agent」。
- 同事的 AI 只能新增記憶與提出疑慮，不能改掉或取代既有知識。

| 17 | 工作筆記（2026-11-25） | 維運單常常是 AI 的答案能解決問題就關單，沒有人走到「確認結論、寫入記憶」那一步，既有排程（jira-auto-log）又只讀 Jira 描述與評論，看不到對話。所以新增一層「工作筆記」（`HRMS_MEMORY_NOTE`）：AI 每次處理完，把本次的分析與答案寫進工作筆記，不需要先確認結論。工作筆記**不是正式記憶，預設不會被查詢工具查到**。`HRMS_MEMORY` 只留重要且確定的結論，由「筆記整理」排程定期從工作筆記整理後寫入。AI 漏寫的部分，使用紀錄只能找出「有查詢但沒有留筆記」的連線；伺服器看不到 AI 有沒有去看程式碼或被使用者修正，所以無法判斷那次是否真的該留筆記。**補漏方式**（2026-11-25）：不做強制，把提醒寫進 MCP 工具本身，只接網址的同事也有效——① 寫筆記工具的說明寫清楚什麼時候要寫；② 查詢工具（`kb_search`、`kb_get`）的回傳結果最後附一行提醒：處理完若有知識庫以外的新結論或使用者的修正，要寫工作筆記。上線後從使用紀錄看「有查詢但沒留筆記」的比例，再決定要不要加強（例如本機 plugin 的結束檢查）。沒有新結論時 AI 不必回報；因此這個比例分不出「判斷過沒有新結論」與「忘了寫」，只能當參考。**定位**：工作筆記存的是每次處理中**知識庫以外**得到的結論。**要存**：查問題過程中另外查出來的新結論（例如去看程式碼得到的）、使用者對 AI 的修正。**不用存**：結論完全來自知識庫 MCP 查詢結果的（知識庫裡本來就有）。單子的結案狀態不另外追蹤或回填，Jira 結案紀錄仍由既有排程（jira-auto-log）在 CS CONFIRM 狀態處理（決策 8），單號關聯沿用決策 7。**升級條件**：之後由一個固定的審核 agent 檢查筆記的結論是否正確，正確才寫入 `HRMS_MEMORY`；這個 agent 之後再建立，現階段先累積筆記（它與第 3 節的「清理 agent」是不是同一個，尚未決定）。欄位見第 4 節；寫入工具是 `kb_note`（2026-11-25 實作，見第 5 節）；保存期限、排程頻率尚未決定，討論過程在 `C:\D\FAQ_web\memory_review\討論清單_記憶寫入機制.html` |

## 3. 清理 agent 要回答的問題

收資料時以這五題為準，確保之後答得出來：

1. 這筆知識是不是重複的？
2. 有沒有人質疑？質疑成不成立？
3. 有沒有被用到？
4. 對不對？（對照來源單號的結案紀錄或程式碼）
5. 該不該升級成 FAQ／SOP／Task？

已知缺口：只知道「被查到」，不知道「被採用」。先不補，跑起來不夠再加。

## 4. 資料表

建表語法：`hrms_kb_online.sql`。資料表已建立（見第 6 節步驟 1），但伺服器還沒有對它們寫入過；不修改任何既有資料表。

| 表 | 用途 |
|---|---|
| `HRMS_KB_USAGE_LOG` | 使用紀錄：時間、使用者、身分來源、電腦位址、連線編號與序號、來源（真人／排程／網站）、用戶端、工具名稱、參數、查詢文字、單號、回傳的知識編號與分數（不存全文）、是否查無資料、寫入結果與指向、耗時、錯誤、伺服器版本、檢索方式版本 |
| `HRMS_KB_CANDIDATE` | 候選：與既有記憶結論不同的新內容。處理結果欄位只由人或清理 agent 更新 |
| `HRMS_KB_FLAG` | 疑慮標記。處理結果欄位只由人或清理 agent 更新 |
| `HRMS_KB_USER_BINDING` | 電腦位址對應使用者。同一位址以最新一列為準。接上公司帳號登入後不再需要 |
| `HRMS_MEMORY_NOTE` | 工作筆記（決策 17）：每次處理的分析與答案，等「筆記整理」排程整理後才進 `HRMS_MEMORY`。欄位：種類（`finding` 新結論／`correction` 使用者修正）、主題、結論、依據、關鍵字、程式入口、單號（`REF_KEY`）、來源（對話／網站／排程）、連線編號、對應的使用紀錄、記錄者、處理結果（待審核／已升級／不採用，只由人或審核 agent 更新）與升級後的記憶編號。不分 System／Engineer，分型留給審核時決定；沒有保存期限欄位。建表語法在 `hrms_kb_online.sql` 第 ⑤ 段；子平於 2026-11-25 建立，共 19 個欄位；同日 `kb_note` 經實際連線寫入第 1 筆（`note#1`，測試資料，主題標明【測試】，待清除）。`USAGE_LOG_ID` 目前不寫（原因見第 5 節工作筆記工具）。表名用 `HRMS_MEMORY_` 開頭是子平指定，表示它與 `HRMS_MEMORY` 是同一組 |

資料表建好之前，伺服器可以用 `KB_STORE=sqlite` 先在本機累積，欄位名稱相同，之後可整批搬入。

### 查詢工具（`tools_query.py`）

| 工具 | 行為 |
|---|---|
| `kb_search(query, sources?, top_k?, jira_key?, customer_code?, version_bulletins?, note?)` | 一次查 Wiki、團隊記憶、FAQ、SOP、Task、Jira 結案紀錄、公告；每個來源各回傳前幾筆（預設 3），分區顯示、不硬排成一條。回傳摘要與編號（如 `[faq#48]`），不含全文與 SQL。`version_bulletins=true` 另外整批列出版更公告。某個來源查詢失敗時會明講，不當成查無資料 |
| `kb_get(type, id, section?, customer_code?)` | 讀單筆全文。Wiki 可指定規則編號、章節名、上半／下半／全文；Jira 可用紀錄編號或單號；`type=custom` 查某客戶的客製（取代 `custom_lookup`） |

- 評分與資料讀取沿用 `servers/MEMORY` 的程式，沒有修改那邊的任何檔案；本機 plugin 的 9 個查詢工具不受影響。
- **不回寫 `HIT_COUNT`**：本機 `recall` 每次命中會把引用次數加一，線上版不做，引用次數改由使用紀錄計算。
- 待處理的疑慮標記會顯示在搜尋結果與全文上（標記的寫入在步驟 4）。
- `kb_search` 帶 `note` 時，伺服器把它存成一筆工作筆記（種類 `process`，主題是「查詢：」加查詢文字，單號取自 `jira_key` 或文字裡的單號），超過 4000 字的部分不存。筆記寫不進去不影響查詢結果。這次呼叫的使用紀錄會同時有查詢結果與 `WRITE_OUTCOME=created`、`WRITE_REF=note#編號`。
- `kb_search`、`kb_get` 有查到東西或查無資料時，結尾附工作筆記提醒，內容帶這個連線的查詢次數與已寫筆數（`Dispatcher.activity()`，只存在記憶體，伺服器重啟歸零）。
- 檢索品質與本機版相同（關鍵字與字詞比對），這一步沒有改善檢索本身；之後用 `shadow_set.db` 量測。

### 寫入工具（`tools_write.py`）

| 工具 | 行為 |
|---|---|
| `remember(kind, purpose, topic, content, keywords?, func_path?, entry_path?, entry_method?, ref_key?)` | 寫入 HRMS_MEMORY。記錄者是伺服器確認過的使用者（如 `amy.lin(AI)`），`SOURCE=kb-online`，用途存在 `META.purpose`。沒有 `supersedes` 與 `force` 參數，帶了也無效 |
| `kb_flag(type, id, reason, evidence, jira_key?)` | 對既有知識提出疑慮。會先確認目標存在；理由與依據都必填。Wiki 可標到某條規則（`CARD#R7`）。不修改原內容 |

`remember` 寫入前的判斷（只在同一型別內比）：

| 情況 | 判斷方式 | 結果 |
|---|---|---|
| 沒有相似的既有記憶 | 相似度（`memory_core._dup_sim`）低於 0.75 | 新增正式記憶 |
| 幾乎相同 | 相似度 ≥ 0.75，且**只比內容本身**的字詞重疊 ≥ 0.90（Engineer 還要入口檔名相同） | 不新增，回覆既有編號 |
| 相似但不是同一個說法 | 相似度 ≥ 0.75 但不符合上一列 | 新內容完整存成候選，並自動幫被撞到的記憶加疑慮標記 |

- 字面比對分不出兩筆的結論是否相反，所以門檻設得保守：寧可多存成候選，不要當成重複丟掉。本機版的做法是 System 型一律當重複，會把相反的結論丟掉，線上版不沿用。
- 0.75 與 0.90 兩個門檻是依少量例子訂的，**沒有用真實資料校準過**。上線後看使用紀錄裡 `candidate` 與 `duplicate` 的比例再調整。
- 用途為 `data_fix` 時，內容裡 ```` ```sql ```` 區塊會用 `task_log` 的同一套檢查；讀取時固定加註「僅供參考」。
- **沒有檢查內容是否含客戶資料**，目前只靠工具說明要求 AI 不要寫。
- 為了讓記錄者是伺服器確認的使用者，`servers/MEMORY/memory_db.py` 的 `insert_memory` 多了一個選填參數 `created_by`；不給時行為與原本相同。這是線上版對 MEMORY 目錄唯一的修改。

### 工作筆記工具（`tools_note.py`，決策 17）

`kb_note(topic, content, kind?, evidence?, keywords?, entry_path?, entry_method?, ref_key?)`：寫一筆工作筆記到 `HRMS_MEMORY_NOTE`，不需要先確認結論、對錯不論。寫不寫看做了什麼動作（讀過程式碼、查過資料表結構、讀過 Jira 單、被使用者糾正），不看有沒有結論（決策 23）。

| 參數 | 欄位 | 說明 |
|---|---|---|
| `kind` | `NOTE_KIND` | 選填，預設 `process`＝過程紀錄（做了什麼、查到什麼、卡在哪）；`finding`＝知識庫以外查出來的結論；`correction`＝使用者對 AI 的修正。資料表補丁（2026-11-25 已套用）套用前，`process` 是存成 `finding`、內容最前面加「〔過程紀錄〕」，且每寫一筆會跳過一個編號（`note#4` 就是這樣空掉的） |
| `topic`／`content` | `TOPIC`／`CONTENT` | 必填；100 字／4000 字 |
| `evidence` | `EVIDENCE` | 依據：程式位置、查證方式，或使用者的原話；選填，2000 字 |
| `keywords`、`entry_path`、`entry_method` | 同名欄位 | 選填。`entry_path` 能轉成 repo 相對路徑就轉，轉不了照原樣存，不因此擋下 |
| `ref_key` | `REF_KEY` | Jira 單號，對話有提到才填（也接受 `jira_key`） |

- 伺服器填的欄位：`CREATED_BY`＝確認過的使用者加 `(AI)`（如 `amy.lin(AI)`）、`ORIGIN`＝連線層的來源、`SESSION_ID`＝連線編號。參數裡帶這些名稱也無效。
- 處理結果欄位（`STATUS`、`RESOLVED_*`、`RESULT_MEMORY_ID`、`RESOLVE_NOTE`）不寫，`STATUS` 用資料表預設值 `open`。
- **`USAGE_LOG_ID` 不寫（留空）**：使用紀錄在工具執行完才產生，而使用紀錄的 `WRITE_REF` 又需要筆記編號，兩邊要同時有值就得回頭 UPDATE 其中一邊；伺服器的資料層只發 SELECT 與 INSERT，所以沒有做。要對回使用紀錄：`HRMS_KB_USAGE_LOG.WRITE_REF = 'note#編號'`（且 `TOOL_NAME = 'kb_note'`），或兩邊相同的 `SESSION_ID`。候選與疑慮標記的 `USAGE_LOG_ID` 也是同樣情況。
- 使用紀錄：成功時 `WRITE_OUTCOME=created`、`WRITE_REF=note#編號`；參數不合格是 `rejected`、寫入失敗是 `failed`。沿用既有的值，沒有動使用紀錄表的 CHECK 限制。因此統計「新增正式記憶」時要用 `TOOL_NAME` 或 `WRITE_REF` 的開頭區分 `memory#` 與 `note#`。
- 不做重複檢查，也不與既有記憶比對：同樣內容寫兩次就是兩筆，判斷留給審核。
- **查詢工具查不到工作筆記**：`kb_search`、`kb_get`、`kb_flag` 都沒有 `note` 這個類型，資料層對這張表只有新增（`add_note`），沒有任何讀取的方法；有單元測試守著這一點。
- 不需要知識庫資料庫（`MSSQL_*` 的查詢用連線）也能寫，只用 store 的連線。
- 漏寫的補法（不強制，決策 23 調整過）：① 工具說明寫成動作觸發；② `kb_search` 與 `kb_get` 有查到東西或查無資料時，回傳結果最後附帶數字的提醒（`tools_query.note_reminder`）；參數錯誤、找不到編號時不附；`kb_search` 可帶 `note` 順手寫；③ 常駐說明有「工作筆記」一節；④ `skill_get` 的對照表有 `note_log` → `kb_note` 一列（本機的對應工具見決策 22）。
- **沒有檢查內容是否含客戶資料**，只靠工具說明要求 AI 不要寫。

### 填寫工具（`tools_contribute.py`）

`kb_contribute(type, title, content, module?, category?, syntax?, notes?, keywords?, description?, updates?, reason?, basis?, jira_key?)`

| 類型 | 寫入的表 | 檢查 |
|---|---|---|
| `faq` | HRMS_FAQ | 模組須為既有值 |
| `sop` | HRMS_FAQ_SOP | 模組須為既有值；內文須依 SOP 模板 |
| `task` | HRMS_TASK | 模組、分類須為既有值；SQL 用 `task_log` 的同一套檢查 |
| `bulletin` | HRMS_FAQ_BULLETIN | 公告類型須為既有值（版更公告用「版本更新」等） |

- 寫入者記為「使用者(AI)」，內文尾端加註「線上填寫；填寫人：某某」與依據。
- **新增**：同一張表有高度相似的內容時不新增，並告知可以帶 `updates` 改成更新那一筆，所以不會卡住。
- **更新**（帶 `updates`）：新增一筆更新版（內文註明「更新自 faq#48」），舊的不動，並在舊的那筆加上疑慮標記「已有更新版本 faq#新編號（填寫人 某某）」。
- 查詢時：經工具寫入的資料顯示「填寫人 某某・未審核」，排序分數乘以 0.9；整批列出版更公告時會另外列出哪幾則是線上填寫的。
- 內容必須來自使用者提供的資料，這點只靠工具說明要求，伺服器無法驗證。
- 與本機 `faq_log`／`sop_log`／`task_log` 的差別：不要求依據必填、Task 不要求先有 Jira 結案紀錄、可以更新人工整理的內容（以新增更新版的方式）、多了公告。
- 為了顯示公告的填寫人，`servers/MEMORY/refdata_db.py` 讀公告時多讀了寫入者欄位。

### skill 與常駐說明（`tools_skill.py`、`online_skills.json`）

- skill 只有一份來源：`plugins/ehrms-tools/skills/<名稱>/SKILL.md`。線上版要提供哪些，由 `online_skills.json` 決定。
- **新增一個線上 skill**：在 `skills/` 加資料夾，再在 `online_skills.json` 加一筆（`name`、`when`、選填的 `note`），重啟伺服器。同事不用做任何事。
- `skill_get` 回傳時會在最前面加一段「本機工具 → 線上工具」對照表，以及該 skill 的線上補充說明（`note`），再接原本的流程全文。這樣 SKILL.md 不用為了線上版另外改寫。
- 需要讀本機程式碼或執行腳本的 skill（bug-fix、debug、custom-sa-analyze 等）不放上來，留在 plugin。
- 目前只提供 `crisis-triage`。`crisis-connection-email` 還在主工作目錄未提交，合併後在清單加一筆即可。
- 常駐說明（連線時自動載入，約 1,600 字）內容：身分確認、查詢方式與依需求的重點、來源優先順序、**每次處理完都要判斷是否寫回**（沒寫要說明原因）、工作筆記的規則（知識庫以外的新結論與使用者的修正用 `kb_note`，沒有就不必說明）、限制、skill 索引。
- 「強制沉澱」目前靠常駐說明要求 AI 每次判斷並說明；伺服器端還沒有強制機制。使用紀錄可以算出「有查詢但沒有寫入」的連線，之後可據此做補沉澱。
- 沒有做 MCP 的提示範本（prompts）；只用工具提供 skill，不依賴各用戶端對 skill 的支援。

所有工具都經過 `Dispatcher.call()`，身分檢查與使用紀錄只寫在這一處。新增工具用 `@registry.tool(...)` 註冊，回傳 `ToolResult`（含回傳的知識編號、寫入結果等），紀錄會自動產生。

## 7. 已知限制與尚未驗證

- **信箱是使用者自己說的**：伺服器只能確認「Jira 名單上有這個人」，不能確認是本人。接上公司帳號登入才會解決。
- **以電腦位址認人**：多人共用同一個對外位址（例如經 VPN）會被當成同一個人。目前前提是同事都在內網。
- **Jira 名單比對尚未對真正的 Jira 測試過**：單元測試用的是假名單。Jira 若因隱私設定不回傳信箱，程式只在搜尋結果剛好一位時接受。
- **資料庫寫入的驗證程度不同**（2026-11-21）：使用紀錄已經由實際呼叫寫進 `HRMS_KB_USAGE_LOG`（含被擋下的呼叫）；使用者對應、候選、疑慮標記只在交易內執行寫入語法後復原，確認語法與欄位正確，還沒有真正留下過資料。
- **`remember` 還沒有真的寫進過 HRMS_MEMORY**：測試都用替身攔下寫入。第一次對真實資料表寫入時要確認記錄者與 `META` 內容正確。
- **重複與候選的門檻未校準**，也沒有擋客戶資料（見寫入工具一節）。
- **來源（ORIGIN）目前一律是真人對話**：排程與網站接上時要加上辨識方式。
- **工作筆記（2026-11-25）**：`USAGE_LOG_ID` 沒有回填（見第 5 節）；沒有重複檢查、沒有擋客戶資料；`HRMS_MEMORY_NOTE` 的 `note#1`（線上版）與 `note#2`（本機 plugin）是實際寫入測試留下的測試資料，主題都標明【測試】，MCP 帳號不能刪，要請人清掉或由審核設為不採用。AI 會不會照提醒去寫筆記，還沒有用真正的 AI 用戶端驗證過；來源（ORIGIN）也只測過 `chat`。試用中的伺服器（連接埠 8780）要重啟才會有 `kb_note`。
- **本機 `note_log`（2026-11-25，決策 22）**：尚未發版，工程師實際使用的 plugin 還沒有這個工具。`ORIGIN` 一律 `chat`：排程是用 `MEMORY_USER` 的排程專用值標示身分，但那個值沒有固定寫法，不能拿來可靠地判斷，所以排程若寫筆記也會記成 `chat`（只能從 `CREATED_BY` 分辨）。FAQ_web 的 AI 助理會把寫入類工具從可用清單移除（`C:\D\FAQ_web\server\services\agent_service.py` 的 `KB_WRITE_TOOLS`），`note_log` 還沒加進去；plugin 更新後若沒加，AI 助理會在決策 19 定案前就拿到這個寫入工具。
- **工作筆記寫入流程調整（2026-11-25，決策 23）**：資料表補丁已套用，但套用後還沒有實際寫入過 `process` 種類的筆記；`note#5` 是套用前寫的，種類仍是 `finding`。連線的查詢次數與筆記數只存在伺服器記憶體，重啟歸零，而且是依連線編號計算，同一個對話若重新連線會從頭算。動作觸發的規則會讓筆記變多、品質變雜（含沒有結論的過程），審核 agent 要能處理；「讀過 Jira 單就寫」也讓筆記更容易帶到客戶資料，仍然只靠說明要求不要寫。本機 plugin 沒有在 `recall` 加 `note`：FAQ_web 的 AI 助理是靠工具名稱清單（`KB_WRITE_TOOLS`）移除寫入工具，查詢工具若能順手寫入，助理就多了一條擋不掉的寫入路徑；線上版的 `kb_search` 有 `note`，之後 FAQ_web 若接線上版也要注意這一點。本機查詢工具的回傳現在會附提醒（9 個查詢工具的內容沒變，只在結尾多一段），FAQ_web 的 AI 助理若用同一個本機伺服器也會看到這段提醒。稽核查詢只涵蓋線上版。
- **Codex 是否支援這種 HTTP 連線與之後的登入流程，尚未查證**。
- **還沒有用真正的 AI 用戶端（Claude Code 等）接上來跑過**：目前的連線測試是用程式直接呼叫工具。AI 會不會照常駐說明先取 skill、處理完會不會做寫回判斷，要實際接上才知道。
